### 1.2 Identify Anomalies
Update anomaly: If the spelling of a formation name is incorrect — for example, "Koobi Fora" is mistakenly stored as "Koobi Forah" in 601 rows — how many rows would you have to update to fix it? What could go wrong during that update?

  - You have to update the 601 rows to fix the incorrect spelling. During the update, you can accidentally change each row in the database or end up two spellings for the formation name.

Insertion anomaly: You want to record a new fossil locality — South Turkwel — before any specimens have been collected there. Can you add it to the flat file? Why or why not?

  - No, every row represents a specimen, so you'd have to introduce placeholder data or a blank row to add anything. 

Deletion anomaly: Every specimen from the Usno Formation is removed from the dataset. What other information about the Usno Formation is lost when those rows are deleted?

  - Everything known about the Usno Formation would be deleted 


Redundancy: The values for country, state_province, subregion, and region are repeated on every row for a given place. For the 601 Koobi Fora specimens, how many times is the value Kenya stored in the country column? What does this mean for the risk of inconsistency?

  - 'Kenya' is stored 601 times, in terms of inconsistency nothing is forcing the copies to agree with one another. 

Questions to answer:
1. In one paragraph, explain why the flat file structure causes these problems.

  - A flat file mixes data about different entities in one row. It includes facts about the specimen: catalog number, element, finder, year, etc. Because place and taxon data are attached to specimens, they are copied onto every specimen that shares them. This is how the abnormalities happen. Fixing the data means editing each copy (Update). A taxon or place cannot exist without a specimen (Insertion), and removing a specimen removes the place or taxon (Deletion). Then the copies are redundant. 

2. What is the fundamental principle that a relational database uses to solve them?

  - Normalization

3. Why does formation belong in localities rather than fossils?

  - A formation is a property where a fossil is found. All other fossils from the assemblage will share the same formation and locality. 

4. What is a foreign key and what does it enforce?

  - A foreign key is a column of values that must match the primary key in another table. It enforces relational integrity within the database. An item can't point to a column that doesn't exist.

5. Why is catalog_number a better primary key for fossils than an auto-incrementing integer in this particular dataset?

  - A catalog number is better as a primary key for fossils because they are already unique identifiers attached to existing skeletal elements. Having a catalog number and auto-generated ID can become confusing and could lead to the same specimen being entered twice with different generated IDs.

Questions to answer:

8. What does SERIAL PRIMARY KEY do that INTEGER PRIMARY KEY does not?

  - A SERIAL PRIMARY KEY creates a background sequence of sequential values for each new row. It automatically inserts the next number; INTEGER PRIMARY KEYs require you to input the numbers manually. 

9. What does REFERENCES taxa(taxon_id) enforce? Write a one-sentence explanation of what PostgreSQL will do if you try to insert a row into fossils with a taxon_id that does not exist in taxa.

  - Every non-null taxon_id in fossils must exist in taxa. 

10. Why are earliest_chronometric_age and latest_chronometric_age stored as NUMERIC rather than TEXT, even though they came from a text file?

  - It is easier to compare and query NUMERIC values rather than TEXT. TEXT compares character by character. NUMERIC stores the values as numbers and makes the database reject non-numbers.
