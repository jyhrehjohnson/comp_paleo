## PART 4 - FIELD SPECIFICATIONS
Questions to answer in week07_answers.txt:

1. Identify one field in your design where you chose NOT NULL and explain why.

  - One field I chose NOT NULL for was the source_id in "Observations." Every character and character state's information can be traced back to a publication or source. Different sources can score characters differently, so a source is essential for recording potential discrepancies.  

2. Identify one field where you deliberately chose to allow NULL and explain what NULL means in that scientific context.

  - A field where I allowed NULL is sex in "specimen". For most hominin fossils, sex is difficult to determine or is undetermined due to preservation or specimen ontogeny. 


3. Are there any fields where you are storing a number as TEXT (or vice versa) for a specific reason? Justify the choice.

  - Catalog numbers are stored as TEXT as they contain a combination of letters, hyphens, and numbers. 


4. Does your design have any fields that store multiple values in one cell (e.g., a comma-separated list of species names)? If so, describe how you would restructure the schema to handle this correctly.

  - Elements preserved under specimen. A single specimen can preserve multiple skeletal elements. For instance, a mandible will have multiple teeth within one element.

## PART 5 — RELATIONSHIPS AND KEYS
Questions to answer:

5. For each table, did you choose a natural key or a surrogate key as the primary key? Justify each choice.

  - Every table uses a surrogate key as the primary key. These ids are unique to the database for referencing and have no real-world meaning. 


6. Does your design have any many-to-many relationships? If so, name the junction table and list its columns.

  - There are three many-to-many relationships: specimen to characters, specimens to taxa, and characters to sources. The junction table would be taxon_assignments. 

    assignment_id  INTEGER PRIMARY KEY
    specimen_id    INTEGER NOT NULL  -> specimen.specimen_id
    taxon_id       INTEGER NOT NULL  -> taxon.taxon_id
    source_id      INTEGER NOT NULL  -> source.source_id


7. Compare your key choices with those made in the OTB schema (catalog_number as a natural TEXT key for fossils; SERIAL integers for taxa and localities). Are your choices consistent with the OTB approach? Where do they differ and why?

  - My choices are similar to the OTB schema for taxa and localities, with both using INTEGER keys. Our specimen tables differ, as the OTB schema has catalog_number TEXT as the primary key for fossils, but my database uses a surrogate specimen_id as the primary key and makes the catalog_number its own unique field. This is because my database draws from specimens across multiple countries that are held in multiple institutions with different cataloging methods. Having a specimen_id as the primary key makes it easier to identify the specimen being referenced.

  - I had to rename rank to taxon_rank and year to pub_year. Both are reserved words in SQL standards. 

9. Choose one table from your schema and explain why each field has the data type you chose.

  - Table: characters

	character_id INTEGER: surrogate primary key. SQLite assigns an INTEGER PRIMARY KEY automatically, and other tables			(character_state, observation) reference it with a single whole number.
 	
	character_name TEXT: a short name such as "sagittal crest". Names vary in length and are words, not quantities.
 	
	character_description TEXT: the full definition as published, which can run to several sentences. TEXT has no length limit 		in SQLite.
 	
	anatomical_region TEXT: a controlled-vocabulary label (cranial vault, face, mandible, dentition, postcranial). It names a 		category, so it is text, not a number code.
 	
	character_type TEXT: a controlled-vocabulary label (binary, multistate, continuous). Stored as words rather than codes 			such as 1/2/3 so that queries and output are readable without a key.
 
	is_ordered INTEGER: a yes/no value. SQLite has no BOOLEAN type, so it is stored as 0 or 1, which can be filtered and 			counted directly. It is left NULL when ordering does not apply (binary and continuous characters).
 
	units TEXT: the unit of measurement for continuous characters (mm, degrees, index). A unit is a label, not a quantity; my 		first draft had this as NUMERIC, which was a mistake.
 
	measurement_protocol TEXT: a free-text description of how the measurement is taken, often citing landmarks.

## PART 8 - DESIGN REFLECTION

On table structure (Ch 5)

11. The textbook describes several characteristics of a well-designed table: it represents a single subject, it has a primary key, it has no redundant data, and it has no multi-value fields. Evaluate one of your tables against each of these criteria.

  - Table: observations

	Single subject: yes. Each row is one scoring of one character by one source. Nothing about the specimen or the character is stored here.
 	Primary key: yes, observation_id.
 	No redundant data: mostly. character_id is probably redundant, since a state already belongs to one character. I kept it because measurements and missing scores have no state, so without character_id those rows would not say which character they belong to.
  	A composite foreign key on (character_id, state_id) prevents the two from contradicting each other.
 	No multi-value fields: yes. Each row holds one state, one measurement, or one missing reason, and a CHECK constraint enforces exactly one of the three.
